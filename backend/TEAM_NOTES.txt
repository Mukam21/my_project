================================================================================
[ГОТОВО] BACKEND 1 — МУКАМ
================================================================================
Зона ответственности: архитектура, домен, бизнес-логика, юнит-тесты,
рекомендации, документация по правилам генерации.

Что сделано:

  domain/
    - User, Action, Category, Achievement, Recap
    - Recommendation (следующий шаг в продукте: code, title, description,
      action_label, category)
    - DefaultAchievements — 7 ачивок с фиксированными порогами

  usecase/ports/
    - UserRepository, ActionRepository, RecapRepository, Cache

  usecase/generator/
    - generator.go      — Execute / Get (метрики → ачивки → рекомендации →
                          save + cache)
    - metrics.go        — подсчёт views/messages/favorites/purchases/sales,
                          top-3 категорий, activity_days
    - achievements.go   — AssignAchievements по порогам (воспроизводимо)
    - recommendations.go — BuildRecommendations: 1–3 CTA без sensitive data

  usecase/profile/
    - ListProfiles / GetByID для тестовых профилей

  delivery/dto/
    - ProfileResponse
    - RecapResponse (полный, с id + user_id)
    - ShareRecapResponse (БЕЗ id / user_id)
    - RecommendationDTO, AchievementDTO, CategoryStatDTO

  tests/unit/
    - generator_test.go
    - achievements_test.go
    - recommendations_test.go
    Все unit-тесты проходят: go test ./tests/unit/... -count=1

  config/
    - загрузка env (Postgres, Redis, CORS, port)

Правила ачивок (зафиксированы в коде):
  curious            >= 500 views
  explorer           >= 1000 views
  social_butterfly   >= 50 messages
  seller_master      >= 5 sales
  shopaholic         >= 10 purchases
  enthusiast         >= 100 activity days
  veteran            >= 300 activity days

Правила рекомендаций (примеры):
  - есть топ-категория     → «Продолжите в „{category}“»
  - много favorites без покупок → «Вернитесь к избранному»
  - были sales            → «Разместите новое объявление»
  - много messages без покупок → «Продолжите диалоги»
  - fallback              → «Исследуйте новые категории»

  backend/internal/usecase/generator/
  backend/internal/usecase/profile/
  backend/internal/usecase/ports/
  backend/internal/delivery/dto/

[ГОТОВО] BACKEND 2 — ИНФРАСТРУКТУРА ДАННЫХ
================================================================================
Зона ответственности: PostgreSQL, миграции, репозитории, seed тестовых
профилей, Redis-кэш.

Что сделано:

  migrations/
    - 001_init.up.sql / .down.sql
        users, categories, actions, recaps
        JSONB: top_categories, achievements, recommendations
    - 002_seed_test_profiles.up.sql / .down.sql
        5 тестовых профилей + bulk actions (generate_series)
        Объёмы достаточны, чтобы на демо срабатывали ачивки

  repository/postgres/
    - user.go   — GetByID, ListProfiles
    - action.go — GetByUserAndYear
    - recap.go  — Save, GetByUserAndYear (включая recommendations)

  repository/redis/
    - recap_cache.go — Get/Set/Delete recap
    - noop_cache.go  — fallback, если Redis недоступен

Тестовые профили (seed):

  Алексей Продавец   11111111-1111-1111-1111-111111111111   seller
  Мария Покупатель   22222222-2222-2222-2222-222222222222   buyer
  Иван Ветеран       33333333-3333-3333-3333-333333333333   veteran
  Елена Новичок      44444444-4444-4444-4444-444444444444   newbie
  Пётр Универсал     55555555-5555-5555-5555-555555555555   universal

Почему PostgreSQL:
  - реляционная модель users/actions
  - JSONB для гибких структур recap
  - воспроизводимые миграции и seed для демо

Почему Redis:
  - кэш recap (TTL 24h)
  - NoopCache, если Redis недоступен — API не падает

Файлы для просмотра:
  backend/migrations/
  backend/internal/repository/postgres/
  backend/internal/repository/redis/

Зона ответственности: UI, пользовательский путь, интеграция с API,

--------------------------------------------------------------------------
1. Экраны / пользовательский путь (обязательный MVP)
--------------------------------------------------------------------------

  A. Выбор профиля
     - GET /api/profiles
     - карточки: avatar, name, profile_type
     - по клику — сохранить выбранный user_id

  B. Старт генерации
     - кнопка «Сгенерировать итоги года»
     - POST /api/recap/generate  { user_id, year: 2025 }
     - состояние loading / error / success

  C. Просмотр итогов (личный recap)
     - показать:
         * счётчики: views, messages, favorites, purchases, sales
         * activity_days
         * top_categories (топ-3)
         * achievements (icon + title + description)
         * recommendations (title + description + action_label)
     - recap должен выглядеть как история, не как «таблица логов»
     - можно разбить на «слайды» / секции (как Stories), чтобы досматривали
       до конца (это прямо в ТЗ)

  D. Share-card
     - GET /api/recap/{user_id}/{year}/share
     - ВАЖНО: в ответе НЕТ id и user_id — не ждать их на фронте
     - кнопка «Поделиться» (скопировать ссылку / web share API)
     - публичная карточка: год, ключевые цифры, ачивки (без PII)

  E. Следующий шаг (возврат в продукт)
     - блок recommendations[]
     - каждая карточка: title, description, action_label
     - по клику на CTA — заглушка/редирект (для MVP достаточно UI-кнопки
       с action_label; deep-link на реальный Avito не обязателен)

--------------------------------------------------------------------------
2. Контракты API (готовы)
--------------------------------------------------------------------------

Base URL (локально): http://localhost:8000

GET /api/profiles  →  200  ProfileResponse[]

  [
    {
      "id": "22222222-2222-2222-2222-222222222222",
      "name": "Мария Покупатель",
      "avatar": "https://i.pravatar.cc/150?img=2",
      "profile_type": "buyer",
      "registered_at": "2020-01-01T00:00:00Z"
    }
  ]

GET /api/profiles/{id}  →  200 ProfileResponse | 400 | 404

POST /api/recap/generate
  Body:
  {
    "user_id": "22222222-2222-2222-2222-222222222222",
    "year": 2025
  }
  → 201 RecapResponse
  → 400 (битый body / лишние поля / плохой year)
  → 404 (неизвестный user)

RecapResponse (личный):

  {
    "id": "…",
    "user_id": "22222222-2222-2222-2222-222222222222",
    "year": 2025,
    "total_views": 1100,
    "total_messages": 55,
    "total_favorites": 160,
    "total_purchases": 14,
    "total_sales": 1,
    "top_categories": [
      { "category": "Недвижимость", "count": 1100 }
    ],
    "achievements": [
      {
        "slug": "curious",
        "title": "Любопытный",
        "description": "Просмотрел более 500 объявлений за год",
        "icon": "👀",
        "category": "views"
      }
    ],
    "recommendations": [
      {
        "code": "browse_top_category",
        "title": "Продолжите в «Недвижимость»",
        "description": "В этом году вы чаще всего смотрели эту категорию — там наверняка есть новое.",
        "action_label": "Открыть категорию",
        "category": "Недвижимость"
      }
    ],
    "activity_days": 180,
    "generated_at": "2026-08-06T00:00:00Z"
  }

GET /api/recap/{user_id}/{year}  →  200 RecapResponse | 404

GET /api/recap/{user_id}/{year}/share  →  200 ShareRecapResponse

  ShareRecapResponse = те же поля, что RecapResponse,
  НО БЕЗ "id" и БЕЗ "user_id".

  {
    "year": 2025,
    "total_views": 1100,
    "total_messages": 55,
    "total_favorites": 160,

    "total_sales": 1,
    "top_categories": [ … ],
    "achievements": [ … ],
    "recommendations": [ … ],
    "activity_days": 180,
    "generated_at": "…"
  }

3. Рекомендации по UI (чтобы закрыть бизнес-ТЗ)
--------------------------------------------------------------------------

  - Не показывать «сырой JSON» — секции/карточки/анимация появления
  - Ачивки — крупные, с emoji (поле icon уже приходит с бэка)
  - Рекомендации — заметный блок в конце («Что дальше?»)
  - Для newbie (Елена) ачивок может не быть — UI не должен ломаться
    на пустом achievements[]; recommendations при этом всё равно есть
  - Обработать loading и ошибки сети / 404
  - CORS уже настроен на localhost:5173 и localhost
