# GoOffer — «Итоги года» (Кейс 3, Avito Start)
MVP веб-приложения, которое превращает годовую активность пользователя на классифайде в **персональный recap**: метрики, ачивки, выводы и понятный следующий шаг внутри продукта.
> Пользователь выбирает тестовый профиль → запускает генерацию → получает связную историю своего года на площадке → видит рекомендации, которые возвращают его в продукт.
---
## Зачем это нужно
| Пользователю | Бизнесу Avito |
|---|---|
| Увидеть свой год: что смотрел, писал, покупал и продавал | Повод вернуть пользователя в продукт |
| Узнать себя в ачивках и категориях | Усилить эмоциональную связь с площадкой |
| Понять, какие возможности доступны дальше | Подтолкнуть к следующему действию (просмотр, чат, объявление) |
**Ключевое отличие от «просто статистики»:** recap — это сценарий. Не сухие цифры, а история + бейджи + CTA.

## Пользовательский сценарий (MVP)
```
1. GET /api/profiles
      → список тестовых профилей
2. POST /api/recap/generate
      { "user_id": "<uuid>", "year": 2025 }
      → сервис считает метрики, назначает ачивки, формирует рекомендации
3. GET /api/recap/{user_id}/{year}
      → полный персональный recap
4. GET /api/recap/{user_id}/{year}/share
      → публичная share-card БЕЗ id и user_id
```
### Пример end-to-end
```bash
# 1. Профили
curl -s http://localhost:8000/api/profiles | jq
# 2. Генерация итогов (Мария — покупатель)
curl -s -X POST http://localhost:8000/api/recap/generate \
  -H 'Content-Type: application/json' \
  -d '{"user_id":"22222222-2222-2222-2222-222222222222","year":2025}' | jq
# 3. Личный recap
curl -s http://localhost:8000/api/recap/22222222-2222-2222-2222-222222222222/2025 | jq
# 4. Share-card (без идентификаторов)
curl -s http://localhost:8000/api/recap/22222222-2222-2222-2222-222222222222/2025/share | jq
```
В ответе generate/get ожидаются поля:
- `total_views`, `total_messages`, `total_favorites`, `total_purchases`, `total_sales`
- `top_categories`, `activity_days`
- `achievements[]`
- `recommendations[]` — следующий шаг в продукте
В share **не должно быть** `id` и `user_id`.

## Тестовые профили
| Имя | UUID | Тип | Характер активности |
|---|---|---|---|
| Алексей Продавец | `11111111-1111-1111-1111-111111111111` | seller | Много продаж, активные просмотры |
| Мария Покупатель | `22222222-2222-2222-2222-222222222222` | buyer | Много просмотров, избранное, покупки |
| Иван Ветеран | `33333333-3333-3333-3333-333333333333` | veteran | Высокая активность почти каждый день |
| Елена Новичок | `44444444-4444-4444-4444-444444444444` | newbie | Мало действий — контраст для демо |
| Пётр Универсал | `55555555-5555-5555-5555-555555555555` | universal | Сбалансированные покупки и продажи |
Данные **детерминированы** (seed в миграциях) → правила генерации воспроизводимы.

## Правила генерации (воспроизводимые)
### Какие действия учитываем
| Тип | Смысл |
|---|---|
| `view` | Просмотр объявления |
| `message` | Сообщение продавцу/покупателю |
| `favorite` | Добавление в избранное |
| `purchase` | Покупка |
| `sale` | Продажа |
### Какие показатели считаем значимыми
- Счётчики по каждому типу действия
- Топ-3 категории по частоте
- Число уникальных дней активности за год
### Ачивки (бейджи)
| Slug | Условие | Смысл |
|---|---|---|
| `curious` | ≥ 500 views | Любопытный |
| `explorer` | ≥ 1000 views | Исследователь |
| `social_butterfly` | ≥ 50 messages | Душа компании |
| `seller_master` | ≥ 5 sales | Мастер продаж |
| `shopaholic` | ≥ 10 purchases | Шопоголик |
| `enthusiast` | ≥ 100 activity days | Энтузиаст |
| `veteran` | ≥ 300 activity days | Ветеран |
Пороги зафиксированы в `domain.DefaultAchievements` + `AssignAchievements` — без «магии».
### Рекомендации (следующий шаг)
Формируются 1–3 CTA по метрикам, например:
- топ-категория → «Продолжите в „Недвижимость“»
- много избранного без покупок → «Вернитесь к избранному»
- были продажи → «Разместите новое объявление»
- много сообщений без покупок → «Продолжите диалоги»
Рекомендации **не содержат** чужих ID, переписок и точных персональных данных.
### Безопасность данных
| Личный recap | Share-card |
|---|---|
| Полная статистика + user_id | Только агрегированные метрики |
| Ачивки и рекомендации | Ачивки и рекомендации без идентификаторов |
| Без переписок и PII других пользователей | Без `id` / `user_id` |

## API
| Method | Path | Описание |
|---|---|---|
| `GET` | `/health` | Healthcheck |
| `GET` | `/api/profiles` | Список тестовых профилей |
| `GET` | `/api/profiles/{id}` | Профиль по UUID |
| `POST` | `/api/recap/generate` | Сгенерировать итоги года |
| `GET` | `/api/recap/{user_id}/{year}` | Получить личный recap |
| `GET` | `/api/recap/{user_id}/{year}/share` | Публичная share-card |
### `POST /api/recap/generate`
```json
{
  "user_id": "22222222-2222-2222-2222-222222222222",
  "year": 2025
}
```
Ответ `201 Created` — объект recap.
Лишние поля в body отклоняются (`DisallowUnknownFields`).

## Архитектура backend
```
backend/
├── cmd/server/ # точка входа, DI, миграции
├── internal/
│ ├── domain/ # User, Action, Recap, Achievement, Recommendation
│ ├── usecase/
│ │ ├── generator/ # метрики, ачивки, рекомендации
│ │ ├── profile/ # работа с тестовыми профилями
│ │ └── ports/ # интерфейсы репозиториев и кэша
│ ├── repository/
│ │ ├── postgres/ # users, actions, recaps
│ │ └── redis/ # кэш recap + NoopCache fallback
│ ├── delivery/ # HTTP handlers, DTO, middleware
│ └── server/ # роутинг
├── migrations/ # SQL up/down
└── tests/
    ├── unit/ # generator, achievements, recommendations
    └── integration/ # полный HTTP-путь на in-memory репозиториях
```
**Clean Architecture:** domain → usecase (ports) → repository / delivery.
Бизнес-правила не зависят от Postgres/Redis/HTTP.
### Почему PostgreSQL
- Реляционная модель пользователей и событий активности
- `JSONB` для гибких структур recap (категории, ачивки, рекомендации)
- Прозрачные миграции и воспроизводимый seed для демо
### Почему Redis
- Кэш сгенерированного recap (TTL 24h)
- Если Redis недоступен — автоматический fallback на `NoopCache`, API продолжает работать

## Продуктовая логика: как достигаем бизнес-цели
1. **Мотивация досмотреть** — ачивки и персональные формулировки («вы чаще всего смотрели Недвижимость»), а не таблица цифр.
2. **Ценность действий** — видно, что именно делал пользователь и какие категории для него значимы.
3. **Возврат в продукт** — блок `recommendations` с конкретным next step (категория / избранное / объявление / чаты).
4. **Безопасный шеринг** — отдельный share-контракт без идентификаторов.
### Как развивать дальше
- Реальные event-stream’ы Avito вместо seed
- Narrative-карточки («ваш год в одном абзаце») через шаблоны или LLM
- Opaque share-token вместо `user_id` в URL
- Сравнение «вы vs среднее по городу» без раскрытия чужих данных
- Push/email с deep-link на recap в конце года
---
## Ограничения MVP
- Нет боевой авторизации Avito — только **тестовые профили**
- Нет доступа к реальным продакшен-событиям
- Share URL всё ещё содержит `user_id` (тело ответа обезличено — достаточно для MVP)
- Рекомендации — продуктовые CTA, не персональные ссылки на конкретные объявления
