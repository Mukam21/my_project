# Gоффер — "Итоги года" (Avito Hackathon, Кейс 3)

MVP веб-приложения для сценария **"Итоги года"**: тестовый профиль → генерация персональной истории → метрики, достижения, рекомендации, story → безопасный share.

Проект создан в рамках **Avito Hackathon** как самостоятельная параллельная реализация кейса 3.

> **Важно:** этот репозиторий является моей самостоятельной реализацией. В процессе разработки я параллельно участвовал в командной работе над основным проектом команды Gоффер. Для этой реализации использовалась общая исходная техническая база и первоначальные frontend/архитектурные решения команды, после чего я самостоятельно развивал проект в отдельном направлении и реализовал дополнительные продуктовые и технические решения.

## Моя зона ответственности

**Архитектура · домен · бизнес-логика · рекомендации · юнит-тесты · документация правил генерации**

В рамках проекта я отвечал за backend-ядро сценария «Итоги года»: как устроены сущности, как из сырых действий пользователя собирается персональный recap, какие ачивки и рекомендации выдаются, и как это покрыто тестами.

### 1. Архитектура

Спроектировал и реализовал слойную структуру backend:

| Слой | Назначение | Основные файлы |
|------|------------|----------------|
| **Domain** | Чистые сущности без инфраструктуры | `internal/domain/` (`User`, `Action`, `Recap`, `Achievement`, `Recommendation`, `CategoryStat`) |
| **Ports** | Интерфейсы репозиториев и кэша | `internal/usecase/ports/` |
| **Use cases** | Бизнес-сценарии (генерация recap, профили) | `internal/usecase/generator/`, `internal/usecase/profile/` |
| **Repository** | PostgreSQL + Redis | `internal/repository/postgres/`, `internal/repository/redis/` |
| **Delivery** | HTTP handlers, DTO, middleware | `internal/delivery/` |

Принципы:
- домен не зависит от БД и HTTP;
- генерация recap тестируется без реального PostgreSQL/Redis (через моки портов);
- кэш (Redis) — ускорение, источник истины — PostgreSQL.

### 2. Домен и бизнес-логика генерации

Пайплайн `Generator.Execute`:

1. Проверка существования пользователя.
2. Попытка отдать recap из кэша.
3. Загрузка действий пользователя за год.
4. Подсчёт метрик (`calculateMetrics`).
5. Назначение ачивок (`AssignAchievements`).
6. Построение рекомендаций (`BuildRecommendations`).
7. Сохранение recap + запись в кэш.

**Метрики** (`metrics.go`):  
просмотры, сообщения, избранное, покупки, продажи, дни активности, топ-категории.

**Ачивки** (`achievements.go`) — прозрачные пороги:

| Slug | Условие |
|------|---------|
| `curious` | ≥ 500 просмотров |
| `explorer` | ≥ 1000 просмотров |
| `social_butterfly` | ≥ 50 сообщений |
| `seller_master` | ≥ 5 продаж |
| `shopaholic` | ≥ 10 покупок |
| `enthusiast` | ≥ 100 дней активности |
| `veteran` | ≥ 300 дней активности |

Правила детерминированы: одинаковые входные действия → одинаковый набор ачивок.

### 3. Рекомендации

`BuildRecommendations` формирует **1–3** следующих шага по метрикам (без PII и чужих данных):

- мало активности → «Начните исследовать Авито»;
- много избранного, мало покупок → «Вернитесь к избранному»;
- есть сообщения без покупок → «Продолжите диалоги»;
- есть продажи → закрепить результат новым объявлением;
- fallback — исследовать новые категории.

Каждая рекомендация содержит: `code`, `title`, `description`, `action_label` (и опционально категорию).

### 4. Юнит-тесты

Покрыта бизнес-логика генерации без поднятия БД:

| Файл | Что проверяется |

| `tests/unit/achievements_test.go` | пороги ачивок |
| `tests/unit/recommendations_test.go` | ветки рекомендаций и лимит в 3 карточки |

Моки портов (`UserRepository`, `ActionRepository`, `RecapRepository`, `Cache`) позволяют изолировать use case от инфраструктуры.
